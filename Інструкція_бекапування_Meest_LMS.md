# Інструкція: резервне копіювання Meest LMS на інший сервер

Ціль: дотриматись правила **3-2-1** (3 копії даних, 2 різні носії, 1 поза сервером) для
платформи, розгорнутої на Ubuntu Server через Docker Compose + Caddy.

Рішення складається з трьох скриптів:

| Скрипт | Що робить | Розклад |
|---|---|---|
| `backup-db.sh` | `pg_dump` бази з контейнера `db` → gzip, ротація 14 днів | щодня 02:00 |
| `backup-media.sh` | `tar` медіа-тому з контейнера `backend` → gzip, ротація 8 тижнів | щонеділі 03:00 |
| `offsite-sync.sh` | шифрує (gpg) нові файли з перших двох скриптів і `rsync`-ить на другий сервер | щодня 04:00 |

Перші два вже готові в проєкті (`/opt/meest-lms/scripts/`) — цей документ пояснює, як
довести до робочого стану весь ланцюжок, включно з офсайт-копією.

---

## 1. Локальні бекапи (backup-db.sh, backup-media.sh)

Ці скрипти лежать в `/opt/meest-lms/scripts/`. Вони нічого не роблять самі —
запускаються лише вручну або по cron.

```bash
chmod +x /opt/meest-lms/scripts/backup-db.sh /opt/meest-lms/scripts/backup-media.sh

# Тестовий прогін — переконайтесь, що обидва відпрацьовують без помилок:
/opt/meest-lms/scripts/backup-db.sh
/opt/meest-lms/scripts/backup-media.sh
```

Якщо все ок, побачите щось на кшталт:
```
2026-09-01T02:00:03+03:00 db backup -> /opt/meest-lms/backups/db/meest_lms_2026-09-01_0200.sql.gz (4.2M)
2026-09-01T03:00:11+03:00 media backup -> /opt/meest-lms/backups/media/media_2026-09-01.tar.gz (312M)
```

**Чому саме так:**
- `pg_dump` виконується *всередині* контейнера `db` (`docker compose exec -T db …`), а не
  копіюванням файлів `pgdata` напряму — копія "живого" каталогу PostgreSQL може вийти
  неконсистентною, якщо в цей момент відбувається запис.
- Медіа архівується всередині контейнера `backend`, де том змонтовано в `/app/media` —
  це саме ті відео/сертифікати, які роздає застосунок.
- Ротація (`KEEP_DAYS=14`, `KEEP_WEEKS=8`) вже вбудована в скрипти — старі файли
  видаляються самі, диск не переповниться.

## 2. Підготовка другого сервера (off-site ціль)

На **другому** (backup) сервері:

```bash
# 1. Створити окремого користувача без sudo-прав
sudo adduser --disabled-password --gecos "" backupuser

# 2. Каталог під бекапи цього проєкту
sudo mkdir -p /backups/meest-lms
sudo chown backupuser:backupuser /backups/meest-lms
```

**Чому окремий користувач:** якщо LMS-сервер колись буде скомпрометовано, зловмисник
матиме лише SSH-ключ, що пише в один каталог одного непривілейованого користувача —
не доступ до всього другого сервера.

---

## 3. SSH-ключ для офсайт-синхронізації

На **першому** сервері (де стоїть LMS), від імені root (бо скрипт бекапу запускається
з-під root через cron):

```bash
ssh-keygen -t ed25519 -f /root/.ssh/id_ed25519_backup -N ""
ssh-copy-id -i /root/.ssh/id_ed25519_backup.pub backupuser@<IP_другого_сервера>

# Перевірка, що ключ працює без пароля:
ssh -i /root/.ssh/id_ed25519_backup backupuser@<IP_другого_сервера> "echo ok"
```

Опційно (рекомендовано) — обмежте, що саме можна робити цим ключем, додавши
префікс у `authorized_keys` на **другому** сервері:
```
command="rsync --server -vlogDtprze.iLsfxC . /backups/meest-lms/",no-port-forwarding,no-X11-forwarding,no-pty ssh-ed25519 AAAA... backup-key
```
Тоді навіть якщо приватний ключ витече, ним можна виконати тільки rsync у цей каталог,
і більше нічого.

## 4. Шифрування (GDPR)

Дамп бази містить email, ПІБ і хеші паролів співробітників — офсайт-копія **має**
бути зашифрована.

```bash
# Згенерувати пароль шифрування і зберегти ЛИШЕ на цьому сервері (для запуску скрипта):
openssl rand -base64 32 > /root/.backup-gpg-passphrase
chmod 600 /root/.backup-gpg-passphrase
```

⚠️ **Обов'язково скопіюйте цей пароль ще й у менеджер паролів окремо від обох
серверів.** Без нього зашифровані бекапи не розшифрувати НІКОМУ, включно з вами —
якщо перший сервер загине разом із цим файлом, офсайт-копія стане марною.

## 5. offsite-sync.sh

Покладіть скрипт `offsite-sync.sh` у `/opt/meest-lms/scripts/` поруч із двома іншими.
Відкрийте його і замініть один рядок під ваше середовище:

```bash
REMOTE_HOST="BACKUP_HOST"   # -> IP або домен другого сервера
```

Що робить скрипт на кожному запуску:
1. Шукає у `backups/db/` і `backups/media/` файли, яких ще немає в зашифрованому
   вигляді в `backups-encrypted/`, і шифрує їх через `gpg --symmetric` (AES256),
   використовуючи пароль з кроку 4.
2. Видаляє зашифровані копії тих файлів, які вже прибрала ротація оригінальних
   скриптів (щоб `backups-encrypted/` не росла нескінченно).
3. Синхронізує `backups-encrypted/` на другий сервер через `rsync` по SSH-ключу
   з кроку 3.

Скрипт **ідемпотентний** — повторний запуск нічого зайвого не робить, шифрує й
відправляє лише нове. Тому його можна запускати щодня, і він сам підхопить як
щоденний дамп БД, так і щотижневий архів медіа, коли той з'явиться.

```bash
chmod +x /opt/meest-lms/scripts/offsite-sync.sh

# Тестовий прогін:
/opt/meest-lms/scripts/offsite-sync.sh
```

Перевірте на другому сервері, що файли дійшли:
```bash
ssh backupuser@<IP_другого_сервера> "ls -lh /backups/meest-lms/db /backups/meest-lms/media"
```
Файли мають бути з розширенням `.sql.gz.gpg` / `.tar.gz.gpg` — якщо видно звичайні
`.gz` без `.gpg`, шифрування не спрацювало, перевірте лог.

## 6. Розклад (cron)

```bash
sudo crontab -e
```
```cron
# База даних — щоночі о 02:00
0 2 * * *  /opt/meest-lms/scripts/backup-db.sh       >> /var/log/meest-backup.log 2>&1

# Медіа — щонеділі о 03:00
0 3 * * 0  /opt/meest-lms/scripts/backup-media.sh     >> /var/log/meest-backup.log 2>&1

# Офсайт-синхронізація — щодня о 04:00 (після обох попередніх)
0 4 * * *  /opt/meest-lms/scripts/offsite-sync.sh     >> /var/log/meest-backup.log 2>&1
```

Порядок часу навмисний: офсайт-завдання о 04:00 гарантовано застає вже готовий
нічний дамп БД (02:00) і, по неділях, свіжий архів медіа (03:00).

---

## 7. Перевірка, що все реально працює

Не довіряйте самому факту "cron налаштовано" — перевірте результат за кілька днів:

```bash
# Лог виконання на першому сервері
tail -50 /var/log/meest-backup.log

# Локальні файли ростуть з правильною датою
ls -lh /opt/meest-lms/backups/db /opt/meest-lms/backups/media

# Зашифровані файли доходять до другого сервера
ssh backupuser@<IP_другого_сервера> "ls -lh /backups/meest-lms/db /backups/meest-lms/media"
```

Рекомендація: додайте просте сповіщення про "мертву руку" (наприклад
[healthchecks.io](https://healthchecks.io), безкоштовний план достатній) — один
`curl` в кінці `offsite-sync.sh`, який пінгує сервіс при успіху. Якщо пінгу не буде
протягом доби, сервіс сам напише на email. Так ви дізнаєтесь про поломку бекапу
одразу, а не через місяць, коли він реально знадобиться.

## 8. Відновлення

### 8.1. Розшифрування (тільки для файлів з другого сервера)

```bash
gpg --batch --yes --passphrase-file /root/.backup-gpg-passphrase \
    -d -o meest_lms_2026-09-01_0200.sql.gz meest_lms_2026-09-01_0200.sql.gz.gpg

gpg --batch --yes --passphrase-file /root/.backup-gpg-passphrase \
    -d -o media_2026-08-31.tar.gz media_2026-08-31.tar.gz.gpg
```

### 8.2. База даних

```bash
cd /opt/meest-lms
gunzip -c backups/db/meest_lms_<дата>.sql.gz | \
  docker compose -f docker-compose.prod.yml exec -T db \
  sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```
Для відновлення на порожню базу — спершу зупинити бекенд і перестворити базу, потім
залити дамп.

### 8.3. Медіа

```bash
cd /opt/meest-lms
docker compose -f docker-compose.prod.yml exec -T backend \
  sh -c 'cd /app/media && tar xzf -' < backups/media/media_<дата>.tar.gz
```

---

## 9. Фінальний чек-лист

- [ ] `backup-db.sh` і `backup-media.sh` виконано вручну без помилок
- [ ] Cron налаштовано на всі три скрипти, лог пишеться в `/var/log/meest-backup.log`
- [ ] `backupuser` на другому сервері без sudo, доступ лише за SSH-ключем
- [ ] Пароль шифрування (`/root/.backup-gpg-passphrase`) збережено **окремо** від обох
      серверів (менеджер паролів)
- [ ] Зашифровані файли (`.gpg`) реально доходять до другого сервера — перевірено
      вручну
- [ ] Виконано **пробне повне відновлення** (БД + медіа) на тестовому середовищі
- [ ] Налаштовано сповіщення про збій бекапу (healthchecks.io або аналог)

Бекап, який жодного разу не відновлювали, юридично існує, але фактично — ні.
